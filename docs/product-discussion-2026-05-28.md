## 一、讨论起点

产品经理提出核心问题：**ANFSF 能否实现从需求输入到完整产出的目标？**

## 二、现有系统真实评估

### 2.1 代码审查发现

基于对全部源码的实际审查，系统能力现状：

**确实能做的**：
- PRD 解析为结构化需求（功能列表、用户流程、数据规范）
- 自动架构决策
- React + TailwindCSS 前端组件生成
- 基础质量检查（安全扫描、代码风格、幻觉检测）

**做不到的**：
- 后端业务逻辑生成
- 数据库迁移脚本
- 完整 CI/CD 部署
- 第三方服务集成

### 2.2 报告与代码的落差

| PHASE-REPORT 声称 | 代码实际 |
|---|---|
| "17 层认知流水线已完成" | 实际串联了 5 层（L1→L4→L6→L7→L10） |
| "四门控质量系统完成" | 多个开关默认 `false`，未默认开启 |
| "自进化系统完成" | 模块存在但**未接入主流水线** |

结论：代码基础扎实（103 测试文件、CI/CD 完整、Docker 就绪），但集成度不足。状态为"模块已就位，编排未完成"。

## 三、平台定位：个人 AI 工具 vs 平台级 AI 工具

### 3.1 核心洞察

目标用户：**软件开发公司**（ANFSF 公司自身及其客户）。

个人 AI 工具解决的是**个人编码效率**，解决不了**团队协作损耗**。

软件开发真正的瓶颈不在打字速度，而在协作损耗：
```
PM 写PRD → 开会讲需求 → 前端理解偏差 → 后端理解偏差 →
前后端各写各的 → 联调时发现对不上 → 返工 → 测试发现问题 →
再返工 → PM说"这和我想要的不一样" → 继续返工...
```

### 3.2 平台差异化价值

| | 个人 AI 工具 | ANFSF 平台 |
|---|---|---|
| 需求理解 | 每个开发各自问 AI，得到三种理解 | PM 确认一次，锁死，所有人看到同一份 |
| 接口契约 | AI 帮前端写一个 mock，帮后端写另一个，对不上 | 从需求直接推导，同一份来源 |
| 代码复用 | 开发凭记忆复制粘贴上次的代码 | 系统自动匹配已验证组件，主动推荐 |
| 联调协调 | 人找人，人等人，人催人 | 提交即触发，自动验证，精准定位问题 |
| 经验传承 | 离职就带走 | 项目做完自动归档，知识留在平台里 |

### 3.3 效率提升估算

| 阶段 | 传统耗时 | 平台方式 | 节省 |
|------|---------|----------|------|
| 需求对齐 | 2-3 次会议+沟通 | 1 次确认 | ~60% |
| 项目脚手架 | 1-3 天 | 几分钟 | ~95% |
| 前后端联调 | 1-5 天 | 几小时 | ~80% |
| 测试反馈循环 | 每轮几小时 | 精确定位 | ~50% |

> ⚠️ 以上为基于行业经验和原型推演的**定性预估**，非实测数据。实际效果取决于 PRD 质量、项目复杂度、团队熟练度等因素。数据将在产品上线后通过度量系统（阶段五）持续收集和校准。

## 四、产品工作流（定稿）

### 4.1 总览

```
阶段零：知识注入（可选但推荐）
    ↓
阶段一：需求确认 + 骨架生成 + 任务分发
    ↓
阶段二：前后端并行开发（含知识积累）
    ↓
阶段三：联调 + 自动化验证 + 部署测试环境
    ↓
阶段四：人工测试 + 分级修复 + 发布
    ↓
阶段五：项目归档与知识回填（系统自动）
    ↓
并行系统：变更管理（贯穿全流程）
──────────────────────────────────────
底层保障：检查点与恢复机制（贯穿全流程）
```

### 4.1.1 检查点与崩溃恢复

流水线的每个阶段在完成时自动写入**检查点**。如果平台崩溃、服务器重启、或流程异常中断——项目从最近的检查点恢复，不需要从头开始。

```
阶段一 → 检查点 1（需求规格 v1 + 骨架代码 + 契约 + 测试脚本）
阶段二 → 无检查点（开发工作在外部的 Gitea，不会丢）
阶段三 → 检查点 3（验证通过的版本快照 + 部署记录）
阶段四 → 检查点 4（测试结果 + 修复记录 + 发布确认状态）
阶段五 → 检查点 5（归档完成标记）

恢复流程：
  ├── 系统重启后扫描所有项目
  ├── 检查每个项目的最新检查点
  ├── 自动从中断位置恢复：
  │     阶段一崩溃 → 重新执行阶段一下半段（骨架/契约/测试生成）
  │     阶段三崩溃 → 重新触发验证流水线
  │     阶段四崩溃 → PM 从上次确认的位置继续
  └── 各阶段内的操作设计为幂等：重复执行不会产生副作用
```

**设计要点**：
- 检查点存储在持久化存储中（数据库或文件系统），不依赖内存
- 阶段一的产物（需求规格、骨架代码、契约文件）作为不可变快照保存在检查点中
- 开发在 Gitea 上的代码提交不受 ANFSF 崩溃影响——那是外部系统
- 长时间运行的 LLM 调用设置超时 + 重试 + 降级机制

### 4.2 阶段零：知识注入（新增）

**目的**：系统不是空白的，先喂知识再做分析。

**三种知识来源与分层**：

```
┌──────────────────────────────────────────────┐
│              知识体系（三层）                   │
├──────────────────────────────────────────────┤
│                                              │
│  第一层：企业沉淀库（竞争力核心）               │
│  ─────────────────────────────               │
│  来源：公司历史项目的 PRD、设计稿、代码仓库、     │
│        测试报告、上线后复盘、组件库              │
│  作用：决定"我们公司怎么做软件"                  │
│       → 组件复用、模板匹配、历史坑点预警         │
│       → 独有壁垒，别人拿不走                     │
│                                              │
│  第二层：竞品情报库（市场对齐）                  │
│  ─────────────────────────────               │
│  来源：ANFSF 自动获取竞品产品信息                │
│  作用：决定"市场上同类产品做到什么程度了"         │
│       → 功能对标、UX 模式参考、差异化提醒        │
│                                              │
│  第三层：行业合规库（准入底线）                  │
│  ─────────────────────────────               │
│  来源：互联网获取行业白皮书、法律法规、           │
│        体系认证标准                             │
│  作用：决定"做这个必须满足什么硬性条件"           │
│       → 合规检查、安全要求、数据规范             │
│                                              │
│  底层：出厂通用基线（系统内置）                  │
│  ─────────────────────────────               │
│  常见软件类型模板（后台管理/数据看板/电商/CMS/    │
│  工作流）、OWASP Top 10 安全基线、行业关键词      │
│  映射（医疗→HIPAA、支付→PCI-DSS、欧盟→GDPR）    │
│                                              │
└──────────────────────────────────────────────┘
```

**竞品情报库的法律与技术限制**：

> ⚠️ 自动获取竞品信息存在法律和技术的双重边界。ANFSF 的竞品情报功能仅限于：(1) 公开可访问的官方文档和产品页面；(2) 客户主动上传的竞品资料；(3) 公开的行业报告和评测。禁止爬取受保护内容、反编译竞品软件、或获取非公开信息。具体实现方案需法务审核。

**知识库的运作模式**：

1. PM 启动新项目时，可选择上传历史参考资料
2. 系统自动从三个库拉取相关信息
3. 竞品库和合规库在后续阶段**只读**，企业沉淀库在阶段五**回写更新**
4. 冷启动模式：知识库为空时，系统依赖出厂通用基线 + 标注"基础质量"，建立心理预期

**三个库在不同阶段的介入方式**：

| 库类型 | 阶段一（需求确认） | 阶段二/三（开发联调） | 阶段四（测试发布） |
|--------|-------------------|---------------------|-------------------|
| 企业沉淀 | 推荐复用组件、提醒历史坑点 | 生成骨架时优先使用已验证组件 | 回归测试重点覆盖历史出过问题的模块 |
| 竞品情报 | 功能对标分析、差异化提醒 | 不介入 | 发布确认时回顾对比 |
| 行业合规 | 合规要求注入需求规格 | 代码安全扫描以合规为基准 | 合规项作为发布检查必过项 |

### 4.3 阶段一：需求确认 + 骨架生成 + 任务分发

**目的**：PM 确认需求，系统一次性完成理解、生成、拆解、分发。

**详细步骤**：

```
步骤 1：PRD 提交
  ├── PM 提交 PRD（文字 + 附件：截图/PDF/CSV/原型稿）
  └── PM 可选：上传历史参考资料（触发阶段零知识注入）

步骤 1.5：PRD 质量预检（新增——防止垃圾进垃圾出）

  系统在正式分析前，先评估 PRD 质量：

  ┌─────────────────────────────────────────────────────────┐
  │  PRD 质量评估维度：                                      │
  │                                                         │
  │  ├── 完整性：是否覆盖了功能描述、用户角色、核心流程？    │
  │  ├── 一致性：PRD 内部是否存在自相矛盾的描述？            │
  │  ├── 可量化性：是否使用了模糊词（"快""多""好看"）        │
  │  └── 可验证性：每个功能点是否可以对应到验收标准？        │
  │                                                         │
  │  质量评分：                                              │
  │  ├── ≥70 分 → 绿灯，直接进入步骤 2                         │
  │  ├── 40-70 分 → 黄灯，进入步骤 2 但标记"需求质量偏低，    │
  │  │              系统将进行更多推断"                       │
  │  └── <40 分 → 红灯，不直接进入分析，而是：                │
  │         → 切换到"需求引导模式"                            │
  └─────────────────────────────────────────────────────────┘

  需求引导模式（PRD 质量过低时触发）：
    
    系统不以 PRD 为基础做分析，而是进入对话式需求澄清：
    
    "我无法从这份文档中足够清楚地理解需求。我们一起来梳理：
     1. 这个系统的主要用户是谁？
     2. 用户使用这个系统要完成的最重要的三件事是什么？
     3. 有没有现成的类似系统可以参考？"
    
    PM 通过对话逐步补充信息，系统实时更新需求理解草稿。
    当草稿质量达到 70 分时，系统提示"需求已经足够清晰，可以锁定了吗？"
    
    这个模式类似一个顾问和客户聊需求，而不是让 PM 面对空白界面不知所措。

步骤 2：系统需求分析
  ├── 系统解析 PRD → 结构化需求
  ├── 系统查询三个知识库 → 补充分析
  │     ├── 企业沉淀库：匹配相似历史项目，推荐可复用组件，标记历史坑点
  │     ├── 竞品情报库：对比竞品功能，输出对标报告
  │     └── 行业合规库：提取合规要求，注入需求规格
  ├── Why-What-How 推理 → 输出需求理解报告
  └── 呈现给 PM → 等待确认

步骤 2.5：需求理解置信度标注（关键——防止 LLM 幻觉在源头污染需求）

  系统在呈现需求理解报告给 PM 之前，先自我标注每一条理解的置信度：
  
  ┌─────────────────────────────────────────────────────────┐
  │  每条需求理解条目必须附带：                               │
  │                                                         │
  │  📌 推导来源：从 PRD 的哪句话/哪个段落推导出来的？        │
  │     ├── 🟢 明确提及（PRD 第 X 段明确写了这条需求）       │
  │     ├── 🟡 合理推断（PRD 说了 A 和 B，系统推断出 C）     │
  │     └── 🔴 系统补充（PRD 没提，但同类项目通常需要）       │
  │                                                         │
  │  📌 置信度：                                            │
  │     ├── 高（95%+）：PRD 明确描述，无歧义                 │
  │     ├── 中（70-95%）：PRD 有描述但存在歧义空间           │
  │     └── 低（<70%）：PRD 未明确，系统基于行业惯例推断      │
  └─────────────────────────────────────────────────────────┘
  
  PM 确认界面上，低置信度条目用红色高亮，中等置信度黄色：
  "以下 3 条是系统推断的，PRD 中未明确描述。请重点确认。"
  
  如果 PM 不确认低置信度条目直接锁死 → 系统警告但不阻止。
  PM 可以调整置信度级别（"这个推断是对的，标记为高置信度"）。

步骤 3：PM 确认（有结构化界面）
  ├── PM 查看：功能列表（带置信度颜色标记）、用户流程图、数据模型推断、竞品对比、合规要求
  ├── PM 重点审查：🔴 低置信度 / 系统推断条目
  ├── PM 操作：逐条确认 / 修改 / 补充 / 标记优先级 / 调整置信度
  ├── PM 可反复与系统对话调整，直到满意
  ├── PM 点击"锁定需求"
  └── 系统生成需求版本 v1 → 锁死，进入下游

步骤 4：技术可行性标记（系统自动，不阻塞流程）
  ├── 系统扫描需求规格
  ├── 标记潜在风险：
  │     ├── 技术矛盾（如"离线实时同步"）
  │     ├── 未定义边界条件（如"大量数据"未定义数量级）
  │     └── 依赖未明确（如"对接第三方 X 系统"但未提供 API 文档）
  └── 风险标记带入骨架，在高风险点生成醒目 TODO

步骤 5：自动生成 E2E 自动化测试脚本
  ├── 根据功能列表 + 用户流程，自动生成可执行的 E2E 测试脚本（Playwright/Cypress）
  ├── 每个用户流程生成对应的自动化脚本，同时生成验收清单给 PM 参考
  ├── 示例：
  │     需求："用户能提交请假申请并查看审批状态"
  │     系统生成：
  │       - 3 个 Playwright 脚本（正常提交、空表单校验、审批流程）
  │       - 1 份验收清单（列出所有自动化覆盖的场景 + 标注无法自动化的场景）
  │     脚本生成质量见第九章（9.8 自动生成脚本的质量预期）
  ├── PM 可以在此阶段审阅验收清单、调整补充场景
  ├── 脚本存入项目的测试代码仓库，随项目代码一起版本化
  └── 脚本首次在阶段三运行时，如有选择器问题，由开发或 PM 微调后永久生效

步骤 6：骨架生成 + 契约生成
  ├── 前端骨架：路由 + 布局 + 页面组件 + 状态管理 + API 调用层
  ├── 后端骨架：路由注册 + 中间件链 + 数据库 Schema + 接口 stub + 参数校验
  ├── 接口契约（OpenAPI）：字段名、类型、必填/可选、错误码定义
  ├── 业务逻辑位置明确标记 TODO 注释（"// TODO: implement approval logic"）
  ├── 技术风险点生成警告级注释（"// WARNING: 离线同步方案待确认"）
  └── 所有产物关联到需求版本 v1

步骤 7：任务拆解与分发
  ├── 生成前端 TASK.md：
  │     ├── 任务清单，每个任务带文件路径 + 行范围建议
  │     ├── 标注依赖关系（"此任务需等待后端接口 /api/xxx 契约就绪"）
  │     └── 优先级排序
  ├── 生成后端 TASK.md：同上结构
  ├── 系统创建开发分支（dev/feature-xxx）
  ├── 分发"开发任务包"：
  │     每个开发者收到：
  │     ├── 一个已初始化的分支（代码能跑起来）
  │     ├── TASK.md（只含自己负责的部分）
  │     ├── 与自己相关的接口契约摘录
  │     └── 需求规格对应部分的引用
  └── 通知相关人员
```

### 4.4 阶段二：前后端并行开发（含知识积累）

**目的**：开发在骨架上填写业务逻辑，系统静默追踪所有代码变动。

**详细步骤**：

```
步骤 1：开发接收任务包
  ├── 拉取分支，代码可立即运行
  ├── 查看 TASK.md → 了解需要补的代码点
  └── 开始填写业务逻辑

步骤 2：每次代码提交 → 系统自动动作
  ├── a. 契约检查
  │     ├── 后端改动是否影响接口契约？
  │     ├── 有影响 → 自动通知前端："字段 X 变为 Y，请关注"
  │     └── 前端改动是否调用了未定义的接口？→ 警告
  │
  ├── b. 代码变动分析（git diff 自动标注）
  │     ├── 骨架未动区域 → 标记为"generated"
  │     ├── 开发修改区域 → 标记为"modified"
  │     ├── 开发新增文件 → 标记为"new"
  │     └── 标注存入项目元数据，作为阶段五组件提取的数据源
  │
  └── c. 安全扫描
        └── 增量扫描本次提交内容，发现漏洞即时通知

步骤 3：开发完成标志
  ├── 开发者将 TASK.md 中的任务逐条勾选完成
  ├── 所有任务打勾 → 系统自动标记"开发就绪，可进入联调"
  └── 通知进入阶段三
```

### 4.5 阶段三：联调 + 自动化验证 + 部署测试环境

**目的**：不设"启动联调"按钮，提交即触发。自动发现问题、定位问题、分发问题。

**详细步骤**：

```
步骤 1：提交即触发
  ├── 任一开发提交代码 → 系统自动触发验证流水线
  └── 不依赖人判断"可以联调了"

步骤 2：自动验证流水线
  ├── Layer 1：契约测试
  │     ├── 对照契约文档，验证每个接口的请求/响应格式
  │     ├── 字段名、类型、必填/可选、错误码 → 全部对照
  │     └── 不匹配 → 记录差异，进入步骤 3
  │
  ├── Layer 2：多接口集成测试
  │     ├── 根据用户流程生成调用链（如"登录→创建订单→查看列表→取消订单"）
  │     ├── 按顺序调用多个接口，检查数据一致性
  │     └── 失败 → 定位到具体出错的接口调用
  │
  └── Layer 3：E2E 测试用例
        ├── 运行阶段一生成的 E2E 用例
        └── 失败 → 定位到具体操作步骤

步骤 3：失败处理——精准定位，不追求全自动路由
  ├── 系统输出故障报告：
  │     问题：接口 /api/approve/:id 返回 500
  │     可能原因：参数 `status` 类型不匹配（期望 string，收到 number）
  │     相关代码位置：backend/src/routes/approve.ts:42
  │                   frontend/src/api/approve.ts:18
  │     建议：由后端修改参数校验 OR 由前端修改传参格式
  │     （系统不确定哪个是正确的，只列出两种可能）
  │
  ├── 创建修复任务 → 通知相关开发者
  └── 开发者认领 → 修复 → 提交 → 重新触发步骤 2

步骤 4：验证通过
  ├── 三层全部通过 → 系统自动部署到测试环境
  ├── 产生环境快照（版本号 + 部署时间 + 代码 commit hash）
  └── 通知 PM："测试环境已就绪，可以开始测试"
```

**4.6.2 分级修复**

| 级别 | 范围 | 处理方式 |
|------|------|----------|
| **L1** | 样式偏移、拼写错误、类型参数不匹配、lint 错误 | **系统自动修复**，提交时附带 autofix 标记。无需人工确认 |
| **L2** | 接口参数调整、字段名修改、简单校验逻辑补充、表单联动 | 系统**生成修复建议**（代码 diff），开发者**一键确认**或拒绝 |
| **L3** | 业务逻辑错误、算法问题、复杂判断、架构调整 | 系统**只定位问题代码位置**，不生成修复建议。开发者自行修改 |

**修复流程**：

```
步骤 3：修复执行
  ├── L1 问题 → 系统自动提交修复
  ├── L2 问题 → 开发者审查 diff → 确认/拒绝 → 提交
  └── L3 问题 → 开发者自行定位修改 → 提交

步骤 4：每次修复提交后 → 自动回归测试
  ├── 重跑全部已通过的测试用例（不止本次修复相关的）
  ├── 全部通过 → 通知 PM "修复已就绪，请确认"
  └── 有退化 → 立即阻断，通知开发者

步骤 5：PM 逐条确认
  ├── PM 在界面上看到：
  │     ├── 失败用例列表
  │     ├── 每个用例的修复状态（已修复/待修复）
  │     ├── 修复方式（L1 自动/L2 开发确认/L3 开发重写）
  │     └── 回归测试结果
  ├── PM 逐条验证 → 确认通过或退回重做
  └── 全部确认 → 进入发布环节
```

### 4.8 并行系统：变更管理

**目的**：需求不是一次性锁死的，但每次变更必须有代价感知，由 PM 在确认代价后做出知情决策。

**设计原则**：
- 任何阶段 PM 都可以提变更，但下游越深代价越大
- 系统不替 PM 做决定，只算账、列影响、等确认
- 已完成的开发工作被变更影响时，不自动回滚，而是标记"待更新"
- 所有变更必须在发布检查第一层闭环，漏一个都卡住

**4.8.1 PM 提变更的入口**

PM 在项目看板的任意节点都可以发起变更。入口设计为两种场景：

```
场景一：PM 自己发现需要改
  项目看板 → 点击"需求变更"按钮 → 进入变更流程

场景二：系统触发提醒（开发或测试中暴露了问题）
  开发标记了"需求疑问" → PM 收到通知 → 
  点击通知 → 进入变更流程（需求原文 + 开发提问一并展示）
```

### 4.9 开发代码的自动修复与知识入库

**背景**：阶段二中，开发在骨架上填写的业务逻辑代码，系统从未"见过"。骨架代码系统认识（自己生的），但开发写的代码是新的——怎么纳入后续的自动修复？怎么从中提取知识？

**核心原则**：

> 宁可漏学十个模式，也不能错修一行逻辑。漏学下次还能再学，错修可能直接上线出事故。

这不是说"允许事故发生"，恰恰相反——**错修一行逻辑的破坏是不可逆的，所以系统必须选择极度保守的修复策略，来确保零自致事故。** 漏学的损失是效率（下次重写），错修的损失是产品（线上出 bug）。两种损失不在一个量级。

**4.9.1 代码来源标注（阶段二已埋桩）**

```
每次 git commit → 系统自动标注每段代码的来源：

┌─────────────────────────────────────┐
│  // [generated] 骨架代码            │
│  import React from 'react'          │
│  const UserList = () => {           │
│                                     │
│  // [modified] 开发修改过            │
│  const handleApprove = async (id) =>│
│      await api.approve(id)          │
│      trackEvent('approve', id)      │ ← 开发加了一行埋点
│                                     │
│  // [new] 开发全新写的              │
│  const checkVipLevel = (user) => {  │
│      if (user.level === 'gold') ... │ ← 系统完全没见过
│  }                                  │
└─────────────────────────────────────┘
```

**4.9.2 修复策略：二维矩阵（代码来源 × 问题类型）**

```
┌──────────────────────────────────────────────────────────────────┐
│  代码来源 →        │  骨架代码    │  开发修改过   │  开发全新写  │
│  ↓ 问题类型        │  (generated) │  (modified)   │  (new)       │
├────────────────────┼─────────────┼──────────────┼──────────────┤
│ 样式偏差           │  L1 自动修  │  L1 自动修   │  L1 自动修   │
│ 拼写/格式          │  L1 自动修  │  L1 自动修   │  L1 自动修   │
│ 类型不匹配         │  L1 自动修  │  L2 建议修   │  L2 建议修   │
│ 接口字段变更       │  L2 建议修  │  L2 建议修   │  L3 只定位   │
│ 未使用变量         │  L1 自动修  │  L2 建议修   │  L2 建议修   │
│ 条件判断缺陷       │  L2 建议修  │  L3 只定位   │  L3 只定位   │
│ 业务逻辑错误       │  - 不存在 - │  L3 只定位   │  L3 只定位   │
│ 算法/公式问题      │  - 不存在 - │  L3 只定位   │  L3 只定位   │
└──────────────────────────────────────────────────────────────────┘
```

**规律**：
- 骨架代码出问题 → 系统可以大胆修（本来就是系统生的，修不坏）
- 开发改过的代码 → 样式格式类自动，有歧义的建议修，逻辑相关只定位
- 开发全新写的代码 → 除了样式拼写这种无争议的，其余一律只告诉你"第几行可能有问题"，不动一个字

**4.9.3 特殊场景：骨架需要重生成，但开发已在上面写了逻辑**

```
需求变更导致骨架区域需要重新生成
  ↓
检查：该区域被开发修改的程度？

轻微修改（< 20% 改动）：
  → 系统基于新需求重新生成骨架
  → 自动合并 (merge) 开发的修改
  → 有冲突 → L2 建议修
  → 通知："骨架已自动更新，请检查第 42 行确认"

大量修改（≥ 20% 或含全新逻辑块）：
  → 系统只标记"此区域需要更新"
  → 不自动重新生成
  → 通知开发："页面需要调整以支持变更 #003，
      当前骨架基于旧需求，建议参考新骨架手动迁移"
  → 系统提供新老骨架 diff 作为参考
```

20% 阈值可由项目配置调整。

**4.9.4 知识提取：从开发代码中学什么**

```
阶段二每次 commit → 系统分析 diff → 提取模式 → 阶段五归档入库 → 下个项目引用
```

**学什么（六类目标）**：

| 提取目标 | 识别方式 | 下个项目的用途 |
|----------|---------|---------------|
| 校验模式 | 检测 if/throw/return 的错误处理块 | 类似场景自动生成同风格校验 |
| 权限判断 | 检测 role/perm/admin 相关条件分支 | 同类需求自动引入权限骨架 |
| 第三方调用 | 检测外部 API 调用（支付、短信、存储） | 同类集成直接复用调用模式 |
| 业务状态机 | 检测连续的 status/state 变更逻辑 | 同领域项目直接引用 |
| 计算公式 | 检测数值计算密集区域 | 标记为参考，不自动套用 |
| 自定义组件 | 检测 [new] 标记的完整组件/模块 | 进入组件入库审核流程 |

**学成什么样**——不是复制代码，而是提炼模式：

```
开发在项目中写了一个审批流转逻辑：
  "部门经理 → 人事 → 总经理（超过3天时）"

系统提取为模式：
  模式名称：多级审批流转
  结构特征：基于 status 字段的分支流转 + 组织架构查询 + 条件触发高级别
  关联关键词：审批、流转、多级、条件

下个新项目 PRD 提到"需要多级审批" →
  系统在阶段一提示：
  "检测到与 proj-2026-005 相似的审批场景。
   历史上采用了三级流转模式（部门→人事→总经办），是否引入？"
```

**不学什么（反向过滤）**：

- 一次性脚本（文件中被修改不超过 2 次）
- 标记为 TODO: refactor / FIXME 的代码
- 在阶段四被标记为 L3 并重写的代码（说明它是错的）
- 违反公司 ESLint/Prettier 规范的代码
- 包含敏感信息的代码（密钥、token、内部地址）

## 五、长期壁垒：积累体系

### 5.1 为什么积累比补齐流水线更重要

软件开发公司的最大浪费不是"写得慢"，而是**每次从零开始重写已经写过的东西**。

补流水线是"长肌肉"，做积累体系是"长大脑"——没有积累，跑通 17 层产出质量也不会递增。

### 5.2 现有底子

| 能力 | 现有模块 | 差距 |
|------|---------|------|
| 模板化 | `src/templates/` | 粒度粗，不支持组合匹配 |
| 组件沉淀 | `src/storage/` + `src/integrations/graphrag.ts` | 没有生命周期管理，只建不查 |
| 经验积累 | `memory-consolidation-skill.ts` + `retrospective-engine.ts` | 不读 git，不做结构化提取 |
| 版本管理 | `src/core/evolution/` | 变更预算和回滚管理存在，未接入主流程 |

### 5.3 与现有 17 层流水线的关系

ANFSF 现有代码实现的是"17 层认知流水线"（L1 PRD 解析 → L2 质量门 → ... → L17 扩展层）。这个蓝图提出的"五阶段工作流"不是替代 17 层，而是**产品化重构**：

- 五阶段工作流是**对用户的抽象**——PM 和开发不需要知道"现在是 L7 还是 L8"，他们只看阶段
- 17 层中的技术能力**下沉为五阶段内部的子步骤**——例如 L10"编译验证"变成阶段三自动化验证的 Layer 1
- 17 层中未被串联的层级（L8 后端生成、L12 数据库迁移、L15-17 扩展层）——它们的技术能力在五阶段对应步骤中逐步启用，不作为独立阶段暴露
- 底线：17 层作为内部架构继续存在，五阶段作为用户界面的产品模型

### 5.4 优先级

| 优先级 | 事项 | 说明 |
|--------|------|------|
| **P0** | UI/UX 模板化（升级现有模块） | 立即可做，效果立竿见影 |
| **P0** | 平台工作流实现（阶段零到五） | 核心价值承载 |
| **P1** | 组件沉淀体系 | 需要新建模块，第二个项目开始提速 |
| **P1** | 三层知识库基建 | 决定长期竞争力 |
| **P2** | 经验积累闭环 | 需要 5-10 个项目数据喂养后才能见效 |
| **P3** | 17 层内部能力持续补全 | 在五阶段框架内逐步启用，不对外暴露 |

## 六、账号与权限体系

### 6.1 设计原则

用户提出的三条核心要求，直接转化为设计原则：

| 要求 | 设计原则 |
|------|----------|
| "每个人都可以看到全过程" | **可见性**：所有角色默认查看项目全貌——需求、进度、代码、测试结果。不做信息隔离 |
| "PM、前端、后端各自做自己的工作" | **可操作性**：写操作按角色授权。前端不能改后端代码，后端不能替 PM 确认需求 |
| "需要授权机制解决企业人员变更" | **角色与人员解耦**：权限授给"项目里的角色"，不授给"具体的人"。人走了角色留下，新人接角色即接权限 |

```
│  2. "后端开发"这个岗位在项目中变为"空缺"状态               │
│  3. 李四已完成的工作：所有权标记为"系统持有"，不随人带走     │
│      ├── 已提交代码：归属不变，历史记录保留                  │
│      ├── 已认领但未完成的任务：自动释放回"待认领"池          │
│      └── 进行中的 L2 修复确认：转交给新的后端开发            │
│  4. 李四持有的平台权限自动失效                              │
│                                                            │
│  场景二：新人接手                                           │
│  ────────────────                                          │
│  项目管理员 → 添加"赵六"→ 分配角色"后端开发"                │
│                                                            │
│  系统执行：                                                │
│  1. 赵六获得"后端开发"在本项目的全部写权限                  │
│  2. 赵六登录后看到：                                       │
│     ├── 项目当前进度                                       │
│     ├── 后端 TASK.md（哪些已完成、哪些待认领）              │
│     ├── 被释放回池的任务列表（"李四遗留的待认领任务"）      │
│     └── 本项目的接口契约和后端骨架代码                      │
│  3. 赵六可以从池中认领任务，开始工作                        │
│                                                            │
│  场景三：PM 交接                                            │
│  ──────────────                                            │
│  更敏感——PM 是需求确认的决策者                              │
│                                                            │
│  交接操作：                                                │
│  1. 旧 PM 的项目操作权限移除                                │
│  2. 新 PM 获得完整的历史上下文：                            │
│     ├── 需求确认记录（哪个版本、改了哪几条、为什么改）       │
│     ├── 变更历史（每次变更的完整影响报告和决策记录）         │
│     ├── 测试进度（通过/失败/待确认的逐条状态）               │
│     └── PM 操作日志（旧 PM 在这个项目里的所有关键决策）     │
│  3. 所有待 PM 确认的事项（发布检查、变更确认等）            │
│     自动转入新 PM 的待办列表                                │
│                                                            │
│  场景四：一人多角色（小团队场景）                           │
│  ─────────────────────────────                             │
│  同一个人可以有多个角色，但权限取最小必要集：               │
│     ├── 张三同时是"前端开发"和"后端开发"                   │
│     ├── 登录后看到前端 TASK.md 和后端 TASK.md              │
│     ├── 可以编辑前端代码也可以编辑后端代码                  │
│     └── 但不能替 PM 确认需求                               │
│                                                            │
└────────────────────────────────────────────────────────────┘
```

### 6.5 关键设计点

**1. "所有权"不跟人走**

代码、测试用例、需求规格的修改历史当然记录具体的人（git blame / 审计日志），但代码的"归属权"属于项目，不属于个人。人走了，代码还在，下一个人可以无缝接手。这是企业级工具和个人工具的根本区别。

**2. Lead 角色：团队内部的确认权**

PM 做需求确认和发布决策，但技术交付的确认（前端交付确认、后端交付确认）可以由对应团队的 Lead 执行。Lead 是角色上的一个标记，不需要单独的账号类型——同一个人既是"前端开发"又是"前端负责人"。

**3. 外部协作权限**

有些场景需要外部人员（客户、外包团队）查看项目进展但不操作。可以有一个"访客"角色——只能看项目看板和测试结果，不能操作任何东西，不能看到源代码。

**4. 审计日志**

所有写操作记录到审计日志：谁、什么时间、做了什么操作、操作前后的状态差异。这对企业场景至关重要——出了问题可以追溯，人员变更时可以还原决策链。

## 七、多项目并行

### 7.1 团队规模约束

**当前实际**：PM（兼测试）1 人、前端 1 人、后端 1 人。项目激增时增加各岗位人数。

**产品化要求**：ANFSF 作为出售产品，必须支持 1 到 N 任意岗位人数的弹性配置，不设最低人数。

### 7.2 两种运行剖面，同一套系统

平台根据团队结构**自动适配**，不需要手动切换模式：

```
系统检查：当前项目每个角色有几个人？

角色人数 = 0 → 该角色相关操作由系统跳过或在发布检查中不要求
角色人数 = 1 → 不分发，任务直接入个人待办
角色人数 ≥ 2 → 开启同角色任务分发机制
```

| 维度 | 1 人团队 | N 人团队 |
|------|---------|---------|
| 任务分发 | 跳过，直接入待办 | 系统推荐 + PM/负责人确认 |
| 同角色协作 | 不触发 | 任务分配、代码审查分工 |
| 跨项目上下文恢复 | **全开**（最需要） | 开启 |
| PM 测试辅助 | **全开**（PM 兼测试） | 转为辅助独立测试人员 |
| 发布检查第三层 | 自动跳过空角色 | 全部角色需确认 |

### 7.3 四类并行场景

```
场景 A：新项目 + 新项目
  核心问题：资源分配、互不干扰

场景 B：新项目 + 推进中项目
  核心问题：新项目如何受益于推进中项目的实时经验

场景 C：新项目 + 已上线项目的功能优化
  核心问题：新项目走完整流程，优化走轻量通道

场景 D：推进中项目 + 已上线项目的功能优化
  核心问题：紧急度不同，人如何分配精力
```

### 7.4 项目隔离与知识流通

项目之间代码隔离，但知识共享：

- **隔离**：代码仓库、需求规格、测试用例、任务清单、人员配置——各项目独立
- **共享**：组件库、模板库、经验库、竞品情报库、行业合规库——所有项目共用同一套

```
项目 A（新项目）→ 读知识库 → 生成骨架 → 开发 → 提取经验 → 回填
项目 B（推进中）→ 读 + 实时标记 → 开发 → 提取经验 → 回填
项目 C（已上线）→ 优化 → 回归测试 → 提取经验 → 回填
                                    ↓
                          企业沉淀库（统一）
```

### 7.5 同角色多人任务分发

系统推荐，人不强制：

```
新任务进来时，系统评估候选人：

1. 当前负载（已在几个项目上？完成率？）
2. 技术栈匹配度（这个任务的技术栈和候选人最近做的接近吗？）
3. 代码熟悉度（候选人之前改过这个模块吗？）
4. 是否已在该项目中（同项目优先，减少上下文切换）

输出：排序推荐列表 → PM/负责人确认或手动改派
```

### 7.6 小团队跨项目上下文恢复

小团队最痛的是"同一颗大脑在三个项目之间跳来跳去，每次切回来忘了写到哪了"。平台的核心价值不是分发任务，而是**缩短上下文恢复时间**：

```
开发打开项目 A 的 TASK.md：

  🔄 UserManagement 搜索功能（正在进行）
     上次提交：2026-05-28 14:30
     提交备注：实现了搜索框 UI，过滤逻辑还未接
     最后编辑：src/components/UserSearch.tsx:42-68
     [点击：打开文件，光标跳到第 68 行]

而不是让开发翻 git log、找文件、回忆两周前写到了哪一步。
```

### 7.7 PM 兼测试时的系统辅助

PM 既是需求提出方又是验收方，存在确认偏差风险。系统充当"第二双眼睛"：

1. **客观对照**：每条测试用例旁展示"需求原文 vs 实际行为"，让 PM 看到措辞差异
2. **需求一致性风险标记**：如需求写了"批量导入"但代码中无批量操作实现 → 主动标记
3. **交叉验证用例生成**：PM 写了 10 条，系统分析覆盖盲区，主动建议补充用例

当团队扩展后有独立测试人员时，这些能力转为辅助测试人员。

### 7.8 已上线项目的优化走轻量通道

已上线项目不做完整五阶段，走简化流程：

```
PM 提交优化需求
  → 系统定位影响范围（涉及哪些文件、与哪些测试用例相关）
  → PM 确认
  → 生成优化任务 → 分发
  → 开发在已有分支上修改 → 提交
  → 自动跑全量回归测试（比新项目更重要——确保旧功能没坏）
  → PM 确认 → 合并上线
  → 优化经验回填到企业沉淀库
```

**技术债务定期扫描**（附加能力，针对长期维护项目）：

> 项目维护超过 6 个月后，系统在每个迭代周期自动扫描技术债务，帮助团队在功能开发和债务清理之间做出知情决策。

```
扫描维度：
  ├── 依赖健康度：过期依赖、已知 CVE 漏洞、主版本落后
  ├── 代码复杂度趋势：圈复杂度持续上升的模块
  ├── 重复代码：跨文件的重复代码块增长
  └── 测试覆盖率变化：覆盖率持续下降的模块

输出：技术债务报告
  ├── 不阻塞开发，仅在项目看板上显示债务评分趋势
  └── PM/技术负责人决定是否将债务项纳入下个优化周期的任务
```

### 7.9 推进中项目的知识实时流通

不用等到阶段五（归档），推进中的项目可以实时贡献知识：

| 模式 | 触发时机 | 知识状态 | 其他项目的引用方式 |
|------|---------|---------|------------------|
| 正式入库 | 阶段五归档 | [已验证] | 系统主动推荐 |
| 实时标记 | 阶段二/三/四持续 | [待验证] | 系统被动展示，PM 自行决定是否引用 |

### 7.10 组织级项目健康度看板

管理者视角的公司级视图：

```
活跃项目列表 + 健康度信号灯：

🟢 正常：所有指标正常
🟡 有阻塞：任务逾期 > 2天 / 联调失败率 > 20% / 某人有变更超48h未确认
🔴 严重：关键路径逾期 > 1周 / 某人负载 > 120% 持续5天 / 发布检查红灯 > 3天未解决

人员负载：每个开发在所有项目上的分配比例、实际完成率、跨项目时间占用
```

## 八、多形态前端输出（移动端支持）

### 8.1 定位修正

ANFSF 的前端产出不是"要么 Web 要么移动端"的二选一，而是**独立 Web 为默认形态，其他形态按需叠加**。

移动端的四种客户需求（融入已有 uni-app App、融入其他厂商 App、融入其他厂商小程序、自适应多屏）不是替代独立 Web，而是补充。

### 8.2 三种输出形态

同一份需求规格（阶段一产出）→ 多通道前端骨架生成 → 各自形态的代码：

```
                    需求规格 v1（所有形态共享）
                           │
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
    ┌──────────┐    ┌──────────┐    ┌──────────┐
    │ 形态 1    │    │ 形态 2    │    │ 形态 3    │
    │ 独立 Web  │    │ H5 嵌入   │    │ 小程序    │
    │ （默认）  │    │ 模块      │    │ 子包      │
    └──────────┘    └──────────┘    └──────────┘

所有形态共用：
  ├── 后端骨架和接口契约（完全一样，只出一份）
  ├── 业务逻辑（开发填一次，跨形态复用）
  ├── 测试用例（共用，加"形态标记"）
  └── 五阶段流程（完全一样）
```

| | 独立 Web | H5 嵌入模块 | 小程序子包 |
|---|---|---|---|
| 适用场景 | 独立部署的 Web 应用 | 融入已有 App 的 WebView | 融入已有小程序的分包 |
| 路由控制 | 自己控制 | 宿主控制 | 宿主控制 |
| 鉴权 | 自己处理 | 宿主传 token | 宿主传 token |
| 宿主通信 | 不需要 | Bridge 协议 | 小程序 API |
| 部署 | 独立部署 | 打包到宿主 或 独立部署 URL | 放宿主分包目录 |
| 响应式 | 是（底层能力） | 是（底层能力） | 小程序自适应 |

### 8.3 阶段一增加部署形态确认

```
PM 在需求确认阶段看到部署形态配置（可多选）：

☑ 独立 Web 项目（默认，始终生成）

☐ H5 嵌入模块
   融入已有 App 的 WebView
   宿主技术栈：[uni-app / RN / Flutter / 原生]
   宿主 Bridge 规范：[上传文档 / 使用通用方案]

☐ 小程序子包
   融入已有小程序的分包
   宿主平台：[微信 / 支付宝 / 抖音]
   宿主框架：[原生 / Taro / uni-app]

屏幕适配（所有形态通用）：
   ☑ 手机  ☑ 平板  ☑ 桌面
```

系统自动检测 PRD 中"融入已有 App/小程序"的信号，提示 PM 勾选。PM 也可以手动增减。

### 8.4 多形态骨架生成

```
形态 1：独立 Web（现成能力）
  → 完整 React 前端项目，独立路由，独立部署
  → 现有逻辑不变

形态 2：H5 嵌入模块（新增）
  → React 代码，但：
    ├── 不接管路由（宿主 App 决定页面加载时机）
    ├── 含 Bridge 适配层：
    │     host.ts（检测宿主环境）
    │     receiver.ts（接收宿主消息：token、用户信息、触发操作）
    │     sender.ts（发消息给宿主：请求原生能力、通知跳转）
    │
    │     ⚠️ Bridge 不是"通用方案"——不同宿主技术栈的 JSBridge 实现不同。
    │     首批支持范围：
    │       - uni-app WebView（优先，与你们现有客户匹配）
    │       - 标准 WebView（Android/iOS 原生 WebView）
    │     后续扩展（有明确客户需求时再支持）：
    │       - React Native WebView
    │       - Flutter WebView
    │     宿主 Bridge 规范由客户提供文档，系统生成对应适配代码。
    │     如客户不提供，系统生成标准方案 + 集成指南，由宿主 App 开发团队适配。
    │
    └── 含模块清单（manifest.json）：
         页面列表、入口说明、宿主需提供的上下文、
         嵌入方式、资源部署方式

形态 3：小程序子包（新增）
  → 小程序原生分包代码（独立目录）
  → 含宿主集成配置：app.json subPackages 注册方式、
    宿主需提供的全局变量、页面跳转路径、第三方插件清单
```

### 8.5 对开发和联调的影响

```
任务清单增加平台标记：

│ 任务              │ 平台标记  │ 说明                      │
├───────────────────┼─────────┼───────────────────────────┤
│ 请假列表页逻辑     │ [共用]   │ 所有平台复用同一份业务逻辑 │
│ 请假列表页 UI     │ [Web]    │ Web 端独立实现            │
│ 请假列表页 UI     │ [H5]     │ H5 端，注意 WebView 适配  │
│ 请假列表页 UI     │ [小程序] │ 小程序原生组件实现        │
│ 审批接口调用       │ [共用]   │ 所有平台共用              │

联调时：
  [H5] 系统提供模拟宿主页面，注入 mock token/Bridge → 可独立测试
  [小程序] 系统提供宿主小程序脚手架 → 子包加载测试
```

### 8.6 优先级

```
P0：响应式 Web（底层能力，所有形态的基础）
P1：独立 Web 骨架（现有，不变）
P1：H5 嵌入模块（覆盖客户情况 1、2，复用现有 React 生成能力）
P2：小程序子包（覆盖客户情况 3，需新建小程序模板体系）
不做：独立 App（React Native / Flutter）——客户已有宿主 App，不需要 ANFSF 再做一个
```

## 九、测试用例治理

### 9.1 核心修正

原方案中，阶段一生成的是"测试用例描述"，PM 在阶段四逐条手动执行。这个设计过于保守。

**修正**：系统从需求规格自动生成的应该是**可执行的 E2E 自动化测试脚本**（Playwright/Cypress），而不只是文字描述。自动化测试脚本作为默认产出，在阶段三就开始跑，PM 的角色从"执行者"变为"审查者"。

### 9.2 测试用例的三个来源

```
┌─────────────────────────────────────────────────────────────┐
│  来源            │ 产出形式          │ 谁产生      │ 维护    │
├──────────────────┼──────────────────┼────────────┼─────────┤
│ 系统自动生成     │ E2E 脚本（可执行）│ 阶段一自动  │ 随需求  │
│ （阶段一）       │ + 验收清单       │            │ 变更自  │
│                  │                  │            │ 动更新  │
├──────────────────┼──────────────────┼────────────┼─────────┤
│ PM 补充          │ 自然语言描述     │ 阶段四测试  │ 系统判  │
│ （阶段四+持续）  │ → 系统判断能否   │ 过程中发现  │ 断能自  │
│                  │   转为自动化脚本 │ 的遗漏场景  │ 动化的  │
│                  │                  │            │ 自动转  │
├──────────────────┼──────────────────┼────────────┼─────────┤
│ 开发补充         │ 单元测试 +       │ 阶段二/三  │ 随代码  │
│ （阶段二/三）    │ 集成测试         │ 开发时     │ 一起    │
└─────────────────────────────────────────────────────────────┘
```

### 9.3 PM 角色的转变

```
修正前：PM 是"测试执行者"
  → 打开界面 → 逐条手动操作 → 手动标记通过/失败

修正后：PM 是"测试审查者"
  → 打开界面 → 看到自动化测试结果：
      通过：45 条（无需关注）
      失败：3 条（系统已自动分类 L1/L2/L3，进入修复流程）
      未覆盖：7 条（自动化做不了，需要 PM 手工验证）
  → PM 的工作：
      1. 审查失败原因（是脚本写错了还是真有 bug）
      2. 执行自动化覆盖不了的 7 条（UX 品味、业务合理性）
      3. 探索性测试（不按脚本，随意操作，发现意外问题）
```

### 9.4 自动化测试的分层执行

```
层级          执行时机            执行内容                  谁来写
─────────────────────────────────────────────────────────────────
L1 单元测试    每次提交            函数级验证                开发
L2 契约测试    每次提交            接口格式验证              系统自动+开发补充
L3 集成测试    每次提交            多接口调用链验证          系统自动
L4 E2E 核心    每次提交            关键路径约 10 条          系统自动
L5 E2E 全量    合并前/每天         全部脚本 50+ 条           系统自动+PM补充
L6 探索测试    阶段四/发布前       无法自动化的场景          PM 手工
```

### 9.5 自动化测试脚本的生命周期

```
阶段一：生成
  需求规格 v1 → 系统自动生成 E2E 脚本
  ├── 每个用户流程生成 1 个脚本
  ├── 覆盖正常路径 + 常见异常路径
  └── 存入项目的测试代码仓库

阶段三：首次运行
  联调通过 → 触发 E2E 脚本执行
  ├── 全部通过 → 进入阶段四
  └── 有失败 → 进入修复循环

阶段四：审查 + 补充
  PM 审查自动化测试结果
  ├── 脚本本身有问题 → 修正脚本
  ├── PM 补充遗漏场景 → 系统判断能否自动化
  └── 不能自动化的 → 加入手工验证清单

阶段四/五：回归
  每次修复提交后 → 重跑自动化测试
  ├── 确认修复有效
  └── 确认没有引入新问题

变更管理联动：
  需求变更 → 系统自动标记受影响的测试脚本
  ├── 简单参数调整 → 系统自动更新
  └── 逻辑变更 → 通知开发手动调整
```

### 9.6 测试脚本的治理规则

```
去重：
  系统检查"这 3 个脚本覆盖同一用户流程的不同分支"→ 合并为参数化脚本

版本化：
  每个测试脚本关联需求规格的版本号
  → 需求 v1.0 的测试脚本集
  → 需求 v1.1 变更导致 3 个脚本更新

跨项目继承：
  PM 在项目 A 补充的测试用例 →
  项目 B 有类似功能时，系统自动提示是否继承

执行优化：
  变更只影响后端接口 → 只跑调用该接口的脚本
  变更只影响前端页面 → 只跑涉及该页面的脚本
  骨架重生成 → 全跑

过期清理：
  需求条目被删除 → 关联的测试脚本标记为"待废弃"
  PM 确认 → 归档或删除
```

### 9.7 自动生成脚本的质量预期（诚实设定）

从 PRD 自动生成可运行的 E2E 脚本是一个已知的技术难题。系统生成的脚本可能遇到：

- **选择器不稳定**：生成的 CSS 选择器在页面结构微调后失效
- **动态内容等待**：异步数据加载后元素才出现，脚本未正确等待
- **环境差异**：测试环境数据与脚本预期的数据不一致

**质量预期**：
- 初始生成的脚本，首次运行通过率预估在 60-80%（取决于页面复杂度）
- 失败不一定代表代码有 bug——脚本本身的选择器可能需要微调
- 系统在首次运行失败后，提供"脚本修正"入口：展示失败的步骤、截图、建议的新选择器
- PM 或开发调整后，脚本修正永久生效。同一脚本在后续运行中应达到 95%+ 的稳定性
- 每次脚本修正的数据反哺给系统，改善下个项目的自动生成质量

这不是 ANFSF 独有的限制，而是整个行业在 AI 自动化测试生成领域当前的现实。诚实地面对它，设计修正机制，比假装自动生成完美可靠更有价值。

### 9.8 自动化不能替代的部分

PM 的手工介入集中在三类自动化做不到的事：

| 类型 | 示例 | 为什么自动化不了 |
|------|------|-----------------|
| 视觉与体验 | "数据看板的配色和公司品牌不搭" | 需要人的审美判断 |
| 业务合理性 | "审批需要三步，实际体验感觉太繁琐" | 需要人的主观感受 |
| 意外发现 | PM 随意操作时发现的边缘问题 | 不在预定脚本路径上 |

这些不是测试体系的缺陷，而是**自动化测试和人工测试的分工边界**——自动化负责"功能正确性"，人负责"产品质量感"。

### 10.1 集成范围

当前需要对接的外部系统：

| 系统 | 类型 | 集成方向 | 用途 |
|------|------|---------|------|
| Gitea（本地搭建） | 代码管理 | 双向 | 仓库创建、代码推送、commit 监听、diff 分析 |

### 10.2 Gitea 对接

```
ANFSF → Gitea（系统自动）：
  ├── 阶段一确认后：创建项目仓库
  ├── 骨架生成后：推送初始代码 + 创建开发分支
  ├── 任务分发时：开发任务关联对应分支
  └── 阶段五归档时：打版本 tag

ANFSF ← Gitea（webhook 监听）：
  ├── 每次 commit → 触发代码标注（generated/modified/new）
  │              → 触发契约检查
  │              → 触发测试分层执行
  ├── 代码 diff → 用于模式提取（阶段五）
  └── 提交历史 → 用于返工检测和经验分析
```

Gitea 有完整的 API 和 webhook 支持，技术对接不复杂。

### 10.3 工单系统：独立产品 + API 对接

**系统边界**：工单系统不应和 ANFSF 做在一起。两者服务于不同阶段、不同用户，部署和运行应独立。

```
┌─────────────────────────┐        ┌─────────────────────────┐
│        ANFSF             │        │       工单系统           │
│     （项目开发平台）       │  API   │     （项目服务平台）       │
│                         │←──────→│                         │
│ 用户：PM/前端/后端        │        │ 用户：客户/客服/运维       │
│ 核心：PRD → 代码          │        │ 核心：反馈 → 服务追踪      │
│                         │        │                         │
│ ┌───────────────────┐   │        │ ┌───────────────────┐   │
│ │ 变更管理 (4.8)     │←──┼────────│ │ 反馈收集（企微入口）│   │
│ │ 修复分级 (4.6.2)   │←──┼────────│ │ 工单路由与追踪     │   │
│ │ 轻量优化 (7.8)     │←──┼────────│ │ 客户状态可见       │   │
│ └───────────────────┘   │        │ └───────────────────┘   │
└─────────────────────────┘        └─────────────────────────┘
```

**为什么不做一个系统**：

| | 做在一起 | 独立 + 对接 |
|---|---|---|
| 部署风险 | 一个挂了全挂 | 互不影响 |
| 权限模型 | 混乱（项目角色 vs 客户角色） | 各自清晰 |
| 产品边界 | 绑定销售 | 可分开卖 |
| 生命周期 | 项目归档后工单挂哪？ | 工单系统跨项目持续运行 |
| 扩展性 | 互相牵制 | 各自独立演进 |

**对接层只需 4 个 API**：

```
工单系统 → ANFSF（反馈触发开发动作）：
  POST /anfsf/api/projects/{id}/feedback
  工单系统通知 ANFSF 有新的客户反馈需要处理

ANFSF → 工单系统（状态回调）：
  PUT /ticket/api/tickets/{id}/status
  ANFSF 通知工单系统修复进度（已确认/修复中/已修复/已发布）

ANFSF → 工单系统（发布通知）：
  POST /ticket/api/releases
  ANFSF 发布新版本后通知工单系统，工单系统通知客户

工单系统 → ANFSF（查询修复状态）：
  GET /anfsf/api/feedback/{id}/status
  工单系统主动查询某条反馈的处理进度
```

**反馈进入 ANFSF 后的路由**：

```
客户反馈进入工单系统
  ↓
系统分类：BUG / 需求变更 / 咨询
  ↓
  ├── BUG →
  │     ANFSF 收到反馈 → 自动关联代码模块 → 评估 L1/L2/L3
  │     PM 确认 → 走轻量优化通道（7.8）
  │     修复完成 → 通知工单 → 通知客户
  │
  ├── 需求变更建议 →
  │     进入变更管理流程（4.8）
  │     PM 决定确认/暂缓/拒绝
  │     确认 → 影响分析 → 任务分发
  │     拒绝 → AI 回复客户原因
  │
  └── 使用咨询 →
        AI 客服直接回复（不经过 ANFSF）
```

### 10.4 客户反馈收集：企微入口 + 工单底座

```
客户视角（极简）：                  ANFSF 内部视角（结构化）：

客户在企微群里说一句话              ┌──────────────────────────┐
  ↓                                │ 工单 #042                │
AI 客服自动处理：                   │ 类型：性能 BUG            │
  1. 接收消息                      │ 来源：客户 X（企微群）    │
  2. 判断分类（BUG/需求/咨询）      │ 关联项目：客户 A-审批系统 │
  3. 追问补充信息（如果需要）       │ 关联模块：订单列表页      │
  4. 结构化存入工单系统             │ 状态：分析中              │
  5. 回复客户："已记录，#042"       │ 客户可见状态：处理中      │
  ↓                                └──────────────────────────┘
客户不离开企微
```

**这个方案的核心**：企微是通道（让客户容易开口），工单是底座（让反馈不被遗忘）。工单底座建好后，以后加微信客服、网页反馈入口、邮件——都是同一个后台。不绑死在一个渠道上。

### 10.5 工单数据的长期价值

工单系统积累的数据是企业沉淀库的重要组成部分：

```
每个已上线项目的工单数据 →
  ├── 最常见的问题类型是什么？
  ├── 哪个模块反复出问题？（→ 下个项目阶段一自动提醒）
  ├── 客户最想要但没做的功能是哪些？（→ 下个迭代的需求输入）
  └── 修复一个线上问题平均要多久？（→ 度量基线）
```

### 10.6 多租户架构

ANFSF 作为出售给多家软件公司的产品，必须保证不同客户之间的数据严格隔离。

**隔离策略**：

```
┌─────────────────────────────────────────────────────────────┐
│  数据层级        │ 隔离方式   │ 说明                          │
├──────────────────┼──────────┼──────────────────────────────┤
│ 项目代码仓库     │ 物理隔离   │ 每个租户独立的 Gitea 组织/仓库│
│ 需求文档         │ 逻辑隔离   │ 同数据库，tenant_id 严格隔离  │
│ 测试用例         │ 逻辑隔离   │ 同上                          │
│ 任务清单         │ 逻辑隔离   │ 同上                          │
│ 企业沉淀库       │ 物理隔离   │ 每租户独立的知识库实例        │
│ 组件库           │ 物理隔离   │ 同上。公司 A 的组件绝不出现在  │
│                  │           │ 公司 B 的推荐列表里            │
│ 经验库           │ 物理隔离   │ 同上                          │
│ 用户与权限       │ 逻辑隔离   │ 租户内角色独立管理            │
│ 工单数据         │ 物理隔离   │ 每租户独立的工单系统实例      │
│                  │           │                               │
│ 出厂通用基线     │ 全局共享   │ 所有租户共享（不含客户数据）  │
│ 竞品情报库       │ 全局共享   │ 匿名化后的行业数据可共享      │
│ 行业合规库       │ 全局共享   │ 法律法规是公共知识            │
└─────────────────────────────────────────────────────────────┘
```

**关键原则**：凡是包含客户项目数据的库——物理隔离。凡是公共知识——全局共享。企业沉淀库永远不会在租户之间流通。

**实现方式**：

- 部署时选择：独立部署（每个客户一套 ANFSF 实例）或多租户共享实例 + tenant_id 隔离
- 独立部署：适合大客户，资源独占，隔离最强
- 多租户共享：适合中小客户，成本更低，靠 tenant_id + 数据库行级安全策略保证隔离
- ANFSF 自身的管理后台需要超级管理员角色，可以跨租户查看系统运行状态但不能查看任何租户的业务数据

### 10.7 私有化部署与断网环境

考虑到部分客户（政府、金融、军工）要求完全隔离的网络环境：

- ANFSF 应支持**完全离线部署**——所有依赖打包，不依赖外部 API
- LLM 层支持对接**本地部署的私有化模型**（如私有化 Qwen、DeepSeek、vLLM 推理服务等），通过 LLM Provider 抽象层切换
- 离线模式下：竞品情报库和行业合规库在联网环境定期导出数据包，离线环境手动导入更新
- 出厂通用基线内置在安装包中，不需要网络

## 十一、成本与 Token 预算模型

### 11.1 为什么必须有成本模型

ANFSF 的每个阶段都依赖 LLM 调用。一个中型项目的完整五阶段流程可能消耗数千万 tokens。如果没有成本控制：

- ANFSF 公司可能每做一个项目就亏损
- 客户收到账单时无法理解费用构成
- PM 不知道"让系统重新生成一次"的边际成本

成本模型不是事后的账单，而是**让 PM 在操作时就能看到代价**。

### 11.2 各阶段的 Token 消耗预估

```
┌─────────────────────────────────────────────────────────────┐
│  阶段          │ 主要 LLM 调用             │ 预估消耗量      │
├────────────────┼──────────────────────────┼────────────────┤
│ 阶段零（知识） │ 历史资料分析              │ 中（可选）      │
│ 阶段一（需求） │ PRD 解析、竞品分析、       │ 高              │
│                │ Why-What-How 推理、        │                 │
│                │ 技术可行性评估              │                 │
│ 阶段一（生成） │ 骨架生成、契约生成、       │ 极高            │
│                │ 测试脚本生成、任务拆解     │                 │
│ 阶段二（开发） │ 代码标注（本地分析为主）  │ 极低（增量）    │
│ 阶段三（联调） │ 故障分析报告生成           │ 低（按需触发）  │
│ 阶段四（修复） │ L1/L2 修复生成             │ 低（按需触发）  │
│ 阶段五（归档） │ 模式提取、经验条目化       │ 中              │
│ 变更管理       │ 影响分析                   │ 低（按需触发）  │
│ AI 客服        │ 客户对话、反馈分类         │ 持续低消耗      │
├────────────────┼──────────────────────────┼────────────────┤
│ 中型项目总计   │                            │ 通常 500万~    │
│ （不含开发对话）│                            │ 2000万 tokens  │
└─────────────────────────────────────────────────────────────┘
```

*注：以上为估算数量级，实际消耗取决于 PRD 复杂度和模型选择。*

### 11.3 模型分层策略

根据任务的重要性和容错率，不同场景用不同模型：

```
┌─────────────────────────────────────────────────────────────┐
│ 模型层级  │ 适用场景                    │ 相对成本  │ 示例   │
├───────────┼────────────────────────────┼──────────┼───────┤
│ 高质模型   │ 需求分析、骨架生成、        │ $$$$     │ 精确  │
│           │ 契约生成、模式提取          │          │ 推理  │
│ 标准模型   │ 测试脚本生成、竞品分析、    │ $$       │ 平衡  │
│           │ 影响分析                    │          │       │
│ 轻量模型   │ 代码标注、故障分类、        │ $        │ 快速  │
│           │ AI 客服                     │          │ 响应  │
└─────────────────────────────────────────────────────────────┘
```

### 11.5 产品定价的几种模式

```
模式 A：按项目收费
  每个项目固定费用，含一定 token 额度，超出另计
  适合：项目制交付的软件公司

模式 B：按席位收费
  每用户/月固定费用，含一定 token 额度
  适合：持续使用的开发团队

模式 C：私有化买断
  一次性购买 license + 年度维护费，客户自带 LLM
  适合：有私有化部署需求的大型客户

模式 D：混合
  基础席位费 + 项目超量费
  对你们当前阶段最务实
```

ANFSF 自身不做 LLM API 的转售——客户可以使用自己的 DashScope/DeepSeek API Key，也可以使用 ANFSF 提供的统一 API（含加价）。两种方式让客户自己选择。

## 十二、LLM 调用架构：直接 API vs 编码智能体

### 12.1 问题的本质

ANFSF 在不同环节需要调用 LLM。但调用方式有两种截然不同的选择：

| | 直接调用 LLM API | 编码智能体（Claude Code/OpenCode 等） |
|---|---|---|
| 工作方式 | 一次对话 → 一次输出 | 多轮对话 → 多步操作 → 最终输出 |
| 能验证自己产出吗 | 不能——生成代码后不运行 | 能——生成→运行→报错→修复→再运行 |
| 代码稳定性 | 取决于 prompt 质量，无人验证 | 经过"生成→验证→修复"闭环 |
| 典型成本 | 低（单次调用） | 高（多轮迭代，token 消耗几倍到几十倍） |

### 12.2 LLM Provider 灵活配置

ANFSF 不绑定具体 LLM 厂商。Provider 通过配置层动态管理，支持增删切换：

```
Provider 配置（灵活可插拔）：
  ├── 多个 Provider 可同时启用（DeepSeek / OpenCode Go / 未来新增）
  ├── API Key 通过环境变量或配置文件注入，不硬编码
  ├── 每个 Provider 下可有多个模型（flash / pro / max 等）
  ├── 模型分层映射：flash→轻量 / pro→标准 / max→高质
  ├── 系统根据任务层级自动选择最优可用模型
  └── 当前 Provider 不可用时自动 fallback 到备选
```

### 12.3 结论：不同环节用不同方式

```
环节                 用什么              原因
─────────────────────────────────────────────────────────
需求分析             直接调 LLM           单次推理，不需要验证
架构决策             直接调 LLM           同上
竞品分析             直接调 LLM           同上
Why-What-How 推理    直接调 LLM           同上
模式提取             直接调 LLM           同上
契约文档生成         直接调 LLM           结构化输出，有 schema 约束
AI 客服回复          直接调 LLM           对话不需要执行
影响分析             直接调 LLM           分析不需要执行
─────────────────────────────────────────────────────────
前端骨架生成         编码智能体            需要保证代码能跑起来
后端骨架生成         编码智能体            需要保证编译通过
测试脚本生成         编码智能体            需要保证能执行
代码修复（L1/L2）    编码智能体            修完之后必须验证
```

**分界线：需要"写出来的代码能跑"的环节——用智能体。只需要"理解和分析"的环节——直接调 LLM。**

### 12.3 编码智能体：自建 vs 外接

确定了代码生成环节该用智能体之后，第二个选择：外接 Claude Code/OpenCode，还是 ANFSF 自建？

**方案 A：外接通用编码智能体**

优点：不需要造轮子，工具已成熟，处理大型代码库的能力已验证。
缺点：成本不可控（Agent 循环消耗大量 token），行为不完全可控（Agent 可能做你不期望的操作），难以深度集成 ANFSF 的特定能力（如骨架生成后立即标注 [generated] 标记）。

**方案 B：ANFSF 自建轻量级 Agent 循环**

优点：完全可控——你的循环、你的验证规则、你的边界。可以深度集成 ANFSF 特定能力。成本可优化——针对骨架生成场景调优，减少浪费。不自作主张——只做你让它做的事。

缺点：需要自己实现"生成→验证→修复"循环。

**建议：方案 B——自建轻量级 Agent 循环。**

> Claude Code 的设计目标是"通用编码助手"，擅长在已有项目里改代码、修 bug、做重构。ANFSF 的场景是从零生成完整项目结构——文件数量大、文件之间有依赖、需要批量创建。这个场景用通用编码助手反而效率低。

### 12.4 ANFSF 自建 Agent 循环设计

```
自建 Agent 循环（仅用于代码生成环节）：

async function generateAndVerify(prompt, outputPath) {
  
  // 第一步：生成
  const code = await llm.generate(prompt)
  await fs.writeFiles(outputPath, code)
  
  // 第二步：验证
  const errors = await runChecks(outputPath)
  // 检查项：编译错误、lint 错误、类型错误、契约不匹配
  
  // 第三步：修复（最多 3 轮）
  let retries = 0
  while (errors.length > 0 && retries < 3) {
    const fix = await llm.generate({
      prompt: `以下代码有下列错误：${errors}。请修复。`,
      context: code
    })
    await fs.applyFix(outputPath, fix)
    errors = await runChecks(outputPath)
    retries++
  }
  
  // 第四步：标记代码来源
  await annotateCodeSource(outputPath)  // [generated] 标记
  
  // 第五步：返回结果（如仍有错误则诚实上报）
  return { code: outputPath, errors, retries }
}
```

这个 Agent 和 Claude Code 的关键区别：**它不探索、不做计划、不自主决策。它只做"生成→验证→修复"这一件事，极度可控。**

### 12.5 与 Claude Code 的互补关系

不排除 Claude Code，保留接口。如果未来某个环节的自建循环不够用（如阶段三的复杂故障自动修复），可以在该环节接入 Claude Code 作为增强。但骨架生成这条核心路径，用自建 Agent 循环。
